# 2026-10-07 — M5: yield to VR games (headless-tested; needs a worn test with a real game)

Done:
- ftrd-stream (both modes) asks ft-screens for the game state ("state" on @ft_screens, every
  0.5 s). While a VR game (SteamVR scene app) runs and Frametop hides its panels in games
  ("ingames hide", the default), the stream steps aside: LiStopConnection (decoder released,
  no video on the Wi-Fi, no encoding on the PC), queued window frames dropped; overlay mode also
  hides its panel and keyboard button (so no laser reaches them, which covers "lasers off in
  games" for the overlay; window mode is a Frametop panel, which Frametop already hides and
  whose lasers follow Frametop's own mode). On game exit it resumes: Remote Monitor through
  Vibepollo's "Resume" control (same monitor, the PC's windows stay put), other apps through
  /resume. `--no-yield` turns it off; with "ingames visible" it keeps streaming.
- FTRD_FAKE_GAME=<file>: the file's existence stands in for a running game (headless tests).
- Remote Monitor starts also release + retry on "not yet capture-ready" (a monitor of this
  client stuck at another size).
- stream.sh cleanup: clears virtual monitors Vibepollo kept after release (release all paired
  identities, then a 3 s start + release each at 2560x1440). stream.sh install-desktop now only
  makes launcher entries for paired identities (Curtis saw dead "monitor 3/4" entries).

Measured (instance 1, window mode, Remote Monitor 2560x1440, fake game):
- streaming: decoder fd open, ~0.4-0.9 MB/s video on Wi-Fi (static desktop)
- suspended in 0.09-0.18 s: decoder fd closed, 0 kB/s
- resumed in 1.4 s via Resume: decoder back, video flowing, same virtual monitor on the PC.

Broke / fixed:
- First suspend crashed the client: frames already queued for the window pointed at capture
  buffers freed by the decoder cleanup ("dup failed: Bad file descriptor" in libwayland). Fix:
  retire the window's buffers and drop the queue right at suspend.
- First resume used libgamestream's /resume for the Remote Monitor: "No running app to resume".
  Fix: launch Vibepollo's Resume control (id 2147483501) instead.
- Leftover virtual monitor (Curtis saw a third screen in Windows' display settings): from these
  tests; Vibepollo's release left it ("Deferring virtual display cleanup until the remaining
  managed client display sessions release ownership"). Cleared with start + release cycles at
  the monitor's own size (1280x720 cycles made it worse: "not yet capture-ready"). Known
  Vibepollo limitation, in 04-milestones.

Next: worn test with a real VR game (Curtis): float both monitors, start a game, check the
panels vanish and the lasers belong to the game, quit the game, check both panels come back
live within a few seconds with Windows' windows where they were.
